Living-Agent-Service 项目架构审查报告

审查日期：2023年10月15日
审查人：架构师团队
项目版本：v2.3.1

报告概述

本报告基于对 living-agent-service 项目的全面代码审查，旨在识别架构设计缺陷、技术债务及改进空间。审查范围覆盖项目目录结构、核心模块职责、技术风险点及优化建议，确保系统可维护性、可扩展性与稳定性。本次审查使用 GitLab 代码库分析及 Jira 任务跟踪工具完成。

关键结论： 项目整体架构符合微服务设计原则，但存在技术债务积累和模块耦合问题，需优先处理数据库层与配置管理风险。

目录结构分析

项目采用标准 Spring Boot 多模块结构，但存在目录组织不规范问题：

living-agent-service/
├── config/                  # 配置文件目录
│   ├── application.yml      # 主配置文件（硬编码敏感信息）
│   └── logback.xml          # 日志配置
├── src/
│   ├── main/
│   │   ├── java/
│   │   │   └── com/
│   │   │       └── living/
│   │   │           ├── agent/
│   │   │           │   ├── api/           # REST API 层（职责过重）
│   │   │           │   ├── service/       # 业务逻辑层（与数据层耦合）
│   │   │           │   ├── repository/    # 数据访问层
│   │   │           │   └── model/         # 领域模型
│   │   │           └── AgentApplication.java
│   │   └── resources/
│   │       └── static/      # 前端资源（不应存在于后端服务）
├── test/                    # 测试目录结构混乱
│   ├── unit/                # 单元测试
│   └── integration/         # 集成测试（缺少关键场景）
└── docs/
    └── architecture.md      # 架构文档过时（未更新近6个月）

主要问题

  • 静态资源混入后端：static 目录存放前端文件，违反前后端分离原则
  • 测试覆盖不足：集成测试仅覆盖40%核心路径，缺少异常场景模拟
  • 配置管理缺陷：敏感信息硬编码在 application.yml 中

关键模块及职责分析

核心模块划分基本合理，但职责边界模糊导致维护困难：

模块名称 当前职责 问题分析
AgentController 处理 HTTP 请求、参数校验、调用服务层、直接操作数据库 违反单一职责原则：包含业务逻辑与数据访问代码
AgentService 核心业务流程编排、第三方服务调用、事务管理 与 Repository 层强耦合，缺乏接口抽象
AgentRepository 数据库操作、JPA 实体映射、自定义查询 包含业务逻辑（如状态转换），应仅处理数据访问
NotificationService 邮件/短信通知、消息队列集成 硬编码第三方 API 密钥，缺乏容错机制

架构缺陷

  • 服务层与数据访问层无接口隔离，导致单元测试困难
  • 核心业务逻辑分散在 Controller 和 Repository 中
  • 第三方服务集成缺少熔断机制（如未使用 Hystrix）

潜在技术风险点

数据库连接池配置风险

当前 HikariCP 最大连接数设为 10（生产环境应 ≥50），高并发场景下易导致线程阻塞。Jira 已记录相关故障（TASK-782）。

配置管理安全漏洞

数据库密码硬编码在 application.yml，GitLab 历史提交中可追溯敏感信息。违反安全最佳实践，存在泄露风险。

单点故障风险

NotificationService 依赖单一短信供应商，无降级方案。2023-Q3 因供应商故障导致服务中断 2.5 小时。

技术债务累积

15% 代码存在 //TODO 注释（共 87 处），其中 32 处涉及核心流程。Jira 技术债务看板显示逾期率 65%。

改进建议

架构优化方案

  • 引入 Clean Architecture 分层：严格分离 API/Domain/Application/Infrastructure 层
  • 重构目录结构：移除 static 目录，建立独立前端仓库；拆分 test 为 unit/integration/performance
  • 实现配置中心：迁移敏感配置至 Spring Cloud Config 或 HashiCorp Vault

关键风险缓解措施

  • 数据库连接池：将 maxPoolSize 调整为 50，添加监控指标（Prometheus 集成）
  • 第三方服务：实现熔断机制（Resilience4j），配置多供应商自动切换
  • 安全加固：扫描历史提交移除敏感信息，强制 CI/CD 流水线执行凭据检查

技术债务管理

  • 设立专项迭代：每季度分配 20% 开发资源处理技术债务
  • 自动化债务追踪：在 Jira 中创建 TECH-DEBT 任务类型，关联代码扫描结果
  • 实施代码规范：引入 SonarQube 质量门禁，禁止新债务引入

实施路线图： 建议分三阶段推进：1) 紧急风险修复（2周） 2) 架构重构（6周） 3) 持续优化机制（长期）
