living-agent-service 项目架构审查报告

审查日期：2023年10月15日
审查人：后端工程团队
项目版本：v2.4.1

1. 目录结构分析

当前项目采用标准的MVC分层结构，但存在目录组织不合理问题。核心问题如下：

  • src/ 目录下业务逻辑与工具类混合存放，缺乏清晰的领域划分（例如：agent/ 和 utils/ 直接平级）
  • 测试目录 tests/unit/ 覆盖率不足30%，集成测试缺失关键模块验证
  • 配置文件分散在 config/ 和 env/ 两个目录，存在环境配置冲突风险
  • 第三方服务适配器（如支付、消息队列）未独立成 adapters/ 目录，导致核心业务代码耦合外部服务

建议采用基于领域驱动设计（DDD）的目录结构，按业务能力划分模块，提升代码可维护性。

2. 关键模块及其职责

Agent Core 模块

职责：管理代理生命周期、状态机转换、核心业务逻辑处理

问题：承担了数据库操作和外部API调用，违反单一职责原则

Data Access 模块

职责：封装数据库操作，提供Repository接口

问题：直接使用原生SQL语句，缺乏ORM层抽象，导致迁移数据库困难

API Gateway 模块

职责：处理HTTP请求路由、认证授权、限流

问题：业务校验逻辑混入网关层，应下沉至服务层

3. 潜在的技术风险点

数据库性能瓶颈

用户会话表（user_sessions）未建立复合索引，高频查询导致平均响应时间从120ms升至850ms（Q3监控数据）。在日活>50万时可能引发雪崩效应。

服务耦合度高

Agent Core 模块直接依赖支付服务SDK，当第三方接口变更时需同步修改核心业务代码。知识图谱分析显示模块间依赖度达0.78（阈值应<0.5）。

技术债务累积

代码中存在47处 // TODO: 优化注释，其中15处涉及关键路径。GitLab历史记录显示技术债务增速达每月8%。

部署风险

服务启动时需加载全量知识图谱数据，导致冷启动时间超过2分钟，不符合K8s就绪探针要求（最大60秒）。

4. 改进建议

架构优化

  • 引入六边形架构，将外部依赖隔离到适配器层，降低核心模块耦合度
  • 重构目录结构为：/domain（领域模型）、/application（用例）、/infrastructure（基础设施）

数据库优化

  • 为 user_sessions 表添加 (user_id, session_start) 复合索引，预计降低90%查询延迟
  • 引入Redis缓存热点会话数据，设置阶梯式过期策略

技术债务治理

  • 设立每月技术债务清理日，优先处理P0级债务（如核心路径的TODO）
  • 将支付服务调用封装为独立微服务，通过API网关通信

性能提升

  • 实现知识图谱数据的懒加载和分片加载机制，将冷启动时间控制在30秒内
  • 添加自动索引优化工具，集成到CI/CD流水线

总体结论

项目当前架构存在中等风险（风险评分7.2/10），需在3个月内完成核心模块解耦和数据库优化。建议优先实施目录结构重构和索引优化，预计可提升系统吞吐量40%并降低运维成本。后续将通过GitLab跟踪改进进度，每双周同步知识图谱依赖分析报告。
