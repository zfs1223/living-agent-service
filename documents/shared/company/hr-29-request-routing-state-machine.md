# 需求路由状态机

## 目标

定义董事长需求从提交到完成的标准状态流，确保每个需求都可追踪、可审批、可回写。

## 状态定义

- `draft`：草稿
- `submitted`：已提交
- `need_clarification`：需澄清
- `assessing`：评估中
- `awaiting_approval`：待审批
- `approved`：已批准
- `routed`：已路由
- `in_progress`：处理中
- `blocked`：阻塞中
- `completed`：已完成
- `rejected`：已拒绝
- `archived`：已归档

## 状态流转规则

### 1. 草稿 -> 已提交

条件：董事长完成需求提交。

### 2. 已提交 -> 需澄清

条件：需求缺少关键字段或存在歧义。

### 3. 已提交 -> 评估中

条件：需求信息完整，可直接初评。

### 4. 需澄清 -> 已提交

条件：董事长补充信息后重新提交。

### 5. 评估中 -> 待审批

条件：系统已给出可行性、成本、周期和风险评估。

### 6. 待审批 -> 已批准

条件：董事长确认继续执行。

### 7. 待审批 -> 已拒绝

条件：董事长决定不做或暂缓。

### 8. 已批准 -> 已路由

条件：系统将任务分发到对应部门或固定员工。

### 9. 已路由 -> 处理中

条件：部门固定员工开始执行。

### 10. 处理中 -> 阻塞中

条件：依赖缺失、审批卡住、权限不足或外部阻塞。

### 11. 阻塞中 -> 处理中

条件：阻塞解除后继续执行。

### 12. 处理中 -> 已完成

条件：交付物完成并通过验证。

### 13. 已完成 -> 已归档

条件：结果写回看板、审计和知识库后归档。

## 处理原则

- 每次状态变更都必须记录原因
- 每次状态变更都必须记录操作者
- 高风险状态变更必须审计
- 任何需求都不应“无状态悬空”

## 呈现要求

前端应至少显示：

- 当前状态
- 责任部门
- 预计完成时间
- 实际完成时间
- 是否需要审批
- 是否阻塞
- 最近一次变更记录
