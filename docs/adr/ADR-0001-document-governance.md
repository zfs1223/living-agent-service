# ADR-0001: 建立文档治理基线（框架文档重构 + PR规则强制检查 + ADR机制启用）

- 状态：已接受
- 日期：2026-04-13
- 决策人：项目维护者
- 相关人员：架构组、核心开发组、评审人员
- 影响模块：docs / .github PR 模板 / 研发评审流程
- 关联文档：
  - `docs/PROJECT_RULES.md`
  - `.github/PULL_REQUEST_TEMPLATE.md`
  - `docs/01-system-overview.md` ~ `docs/07-deployment-operations.md`
  - `docs/adr/README.md`

## 背景

项目文档长期存在三类问题：

1. **框架文档与实现细节混杂**：核心文档中包含大量阶段性状态描述（如完成度、功能清单），导致“架构边界”不清晰。
2. **评审与规则脱节**：虽然已有规则意识，但 PR 过程中没有强制对照项，难以保证新增改动不偏离核心框架。
3. **架构决策不可追溯**：重大决策缺乏统一沉淀格式，后续维护难以回答“为何这样设计”。

## 决策

采用统一文档治理方案，包含三项：

1. **重构核心框架文档（01~07）**：
   - 统一为“框架层粒度”，强调边界、约束、流程、扩展点；
   - 移除阶段性实现汇报内容；
   - 增加代码锚点和框架缺口说明。
2. **将项目规则接入 PR 模板并强制勾选**：
   - 在 `.github/PULL_REQUEST_TEMPLATE.md` 中加入 `PROJECT_RULES` 检查项；
   - 要求对权限先行、统一抽象、知识分层、进化门禁、可观测与回滚逐项确认。
3. **启用 ADR 机制**：
   - 新增 `docs/adr/` 目录规范与模板；
   - 规定架构变更必须新增/更新 ADR。

## 备选方案

- 方案A：保持现状，仅补充说明文档
  - 优点：改动最小
  - 缺点：无法形成强约束，治理问题会重复出现

- 方案B：只启用 ADR，不改 PR 模板
  - 优点：决策可追溯
  - 缺点：日常改动缺少执行门禁，偏离风险仍高

- 方案C（采用）：框架文档重构 + PR 强制检查 + ADR 启用
  - 优点：同时覆盖“定义、执行、追溯”三个层面
  - 缺点：团队初期需要适应新的提交与评审习惯

## 关键权衡

- 用少量流程成本（PR 多几项勾选）换取长期架构一致性与可维护性。
- 文档强调“框架稳定性”而非“阶段进度”，降低文档快速失真风险。

## 影响范围

- 系统层：无运行时代码行为变化。
- 数据层：无数据结构变化。
- 组织/流程：PR 与评审流程新增强制检查；架构变更需要 ADR。
- 成本与风险：短期沟通成本上升；中长期返工和架构漂移风险下降。

## 迁移/实施计划

- 步骤：
  1. 落地核心框架文档重构（已完成）
  2. 接入 PR 模板强制检查（已完成）
  3. 启用 ADR 模板与索引（已完成）
  4. 将后续架构改动纳入 ADR 工作流（进行中）
- 里程碑：
  - M1：文档与模板落地
  - M2：首个架构改动开始按 ADR 提交流程执行
- 回滚：
  - 可回退到旧模板与旧文档，但不建议。

## 验证与度量

- 验证方式：
  - 新 PR 是否完整填写规则勾选项
  - 架构变更 PR 是否附带 ADR 链接
  - 评审意见中“架构偏离类问题”是否下降
- 观测指标：
  - ADR 覆盖率（架构改动 PR 中带 ADR 的比例）
  - PR 模板完整填写率
  - 因架构不一致导致的返工数量

## 风险与缓解

- 风险点：模板项过多，开发者可能“机械勾选”。
- 缓解措施：评审阶段抽查关键项（权限先行、回滚路径、知识/进化规则）并要求证据链接。

- 风险点：ADR 编写质量不稳定。
- 缓解措施：在 `adr/README.md` 中持续补充优秀样例，建立最小质量标准。
