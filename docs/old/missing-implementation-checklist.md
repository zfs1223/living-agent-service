# 逐项对照 `docs/old/` 与当前代码后的缺失实现清单

> 本文档用于在已完成框架澄清之后，进一步把“旧框架文档”逐项对照“当前代码实现”，列出**缺失实现**、**已修复项**、**仍需收尾项**，并给出修补顺序。  
> 本文档会随着代码推进持续更新，当前版本已反映一轮较大规模的实现收口。

## 1. 使用说明

### 1.1 目标

- 不再讨论概念是否存在，而是确认哪些功能**已经在代码里**，哪些仍然只是文档/占位/空壳
- 将缺失项按模块、链路和风险分层，方便逐步修补
- 只列出“会影响企业生命体闭环”的缺失项

### 1.2 判定标准

以下情况记为“缺失实现”：

- 文档已定义，代码中无对应类/接口/配置/处理流程
- 代码有类，但方法为空、逻辑明显未接入、仅占位
- 代码已存在，但未与主流程、权限、审计、状态机、治理联动
- 代码有局部实现，但与旧框架定义不一致，导致流程断点

### 1.3 结构

本清单按旧文档逐项对照：

- `01-system-overview.md`
- `02-core-architecture.md`
- `03-employee-model.md`
- `04-knowledge-system.md`

## 2. 总体缺失结论（已更新）

当前代码的主要缺失，已经从“很多模块不存在”收敛为以下几类：

1. **入口前置门禁仍需继续统一到所有入口**
2. **少量内存实现仍需要进一步生产化/持久化**
3. **跨域编排已建立，但部分业务语义还能再统一**
4. **部分运维、恢复、看板、审计还需要更严格的收口**
5. **文档到代码的映射已大幅补齐，但仍需持续维护**
6. **自我优化能力已具备基础建议链路，但仍需更明确的执行闭环**

> 说明：这一轮中，员工、知识、进化、任务、绩效、仪表盘等主链路已补了大量实现，原来标记为“明显缺失”的控制器、治理层、桥接层，很多已经完成收口。

## 5. 自我优化与自动收敛（新增）

当前系统已经具备了基础的建议与审计链路，但要让它“自己逐步优化完善”，建议把能力分成三层：

### 5.1 自动发现

- 监控异常率
- 绩效波动
- 进化失败率
- 知识回滚率
- 补偿异常

### 5.2 自动建议

- 任务复盘建议
- 绩效优化建议
- 进化复核建议
- 知识晋升建议
- 补偿策略建议

### 5.3 人工确认后收敛

- 建议先进入审阅队列
- 关键规则需要人工批准
- 批准后才进入配置/规则收敛

## 6. 优先级建议（已更新）

### 高优先级

1. 进化结果持久化
2. 员工补偿持久化
3. 绩效评估持久化

原因：

- 这三块是业务闭环的核心结果
- 会直接影响审计、看板和治理
- 当前以内存为主，风险最大

### 中优先级

4. 桥接层语义统一
5. Dashboard 指标分组
6. 自我优化建议链路打通

原因：

- 这些模块不会直接导致数据丢失
- 但容易造成边界混乱
- 也决定系统是否能持续自我收敛

### 低优先级

7. 旧文档维护
8. 当前对照版继续补充细节

原因：

- 主要是维护效率问题
- 不会立即影响业务稳定性

## 7. 落地方式建议

### 7.1 不要一次性大重构

建议按“保留内存版 + 新增持久化版 + 切换默认 Bean”的方式演进。

### 7.2 不要先改 controller 协议

现有 API 协议已经能支撑当前闭环，优先保持兼容。

### 7.3 先做结果型数据，再做聚合型数据

优先顺序：

- 结果（result / record / assessment）
- 明细（feedback / compensation record / indicators）
- 聚合（ranking / dashboard / summary）

### 7.4 自我优化先从“建议”开始

先让系统持续输出建议与风险提示，再由人工确认执行；不要让系统直接修改核心规则。

1. `InMemoryEvolutionResultRepository` → 持久化实现
2. `InMemoryEvolutionFeedbackService` → 持久化实现
3. `InMemoryEmployeeCompensationService` → 持久化实现
4. `InMemoryPerformanceAssessmentService` → 持久化实现
5. `DashboardDataService` 仅做聚合分组整理
6. 再检查桥接层语义是否仍有越界

---

## 9. 验收口径

每做完一个阶段，都建议检查：

- 重启后数据是否还在
- 现有 API 是否兼容
- 看板是否还能正确聚合
- 文档是否仍然与代码一致
- 是否仍存在 Memory / Knowledge / Business 边界混层
- 系统是否开始产出可操作的优化建议

---

## 10. 结论

当前最合适的推进方式不是继续散点补文件，而是按下面顺序推进：

1. 进化结果生产化
2. 员工补偿生产化
3. 绩效生产化
4. 桥接层收口
5. 文档持续对齐
6. 建立“建议—审阅—执行—审计”的自我优化闭环

这条路线能最大程度减少返工，同时保证当前已经建立好的边界不被打乱，并逐步让系统具备持续完善自己的能力。
