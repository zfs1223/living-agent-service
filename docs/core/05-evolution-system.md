# 进化系统设计

> Living Agent Service 进化系统设计
>
> 本文档按“旧架构 vs 当前实现”对照整理，并补充边界定义，避免把历史构想误当成当前现状。

## 一、边界定义

### 1.1 进化系统的边界

进化系统只负责"系统如何演进"，不负责"系统如何接入"。

它关注的是：
- 进化信号如何进入系统
- 进化策略如何选择
- 进化结果如何执行
- 进化失败如何回滚
- 进化结果如何被记录和审计

它不直接负责：
- 聊天入口路由
- 员工身份切换
- 页面导航
- 通用业务 CRUD

### 1.2 旧架构与当前实现的边界

- **旧架构**：更大的"企业生命体式自我进化"愿景，包含技能生成、岗位能力演进，知识沉淀、绩效联动
- **当前实现**：聚焦 `brain-models` 自动调整、回滚、审计

两者不是同一层级的完整度：
- 旧架构是设计愿景
- 当前实现是可运行的落地子集

## 二、旧架构 vs 当前实现

| 维度 | 旧架构 | 当前实现 |
|---|---|---|
| 进化目标 | 企业生命体式自我进化，包含技能生成、岗位能力演进，知识沉淀、绩效联动 | 聚焦 `brain-models` 自动调整，回滚、审计 |
| 信号来源 | 对话、日志、指标、用户反馈等广义信号 | `EvolutionSignal` + `EvolutionResult` + 反馈统计 |
| 核心策略 | `REPAIR` / `OPTIMIZE` / `INNOVATE` / `DEFER` / `ESCALATE` | `REPLACE_MODEL` / `DOWNGRADE_MODEL` / `UPGRADE_MODEL` / `DEFER` / `ESCALATE_TO_ADMIN` |
| 执行对象 | 修改技能代码、更新技能配置、注册新技能，写回知识库 | 调整 brain 与模型的绑定关系 |
| 风险控制 | 门禁、审批、熔断，回滚、知识/绩效/运营联动 | 调度重试，手工回滚、审计历史、可观测输出 |
| 结果回写 | 技能注册，知识库、绩效、运营评判，进化记忆图 | `EvolutionResult`、`EvolutionFeedback`、`BrainModelChangeHistory` |
| 管理入口 | 概念上存在，但偏治理框架 | `EvolutionAdminController` 提供反馈、自动调整、回滚、历史查询 |
| 调度机制 | 概念性的定时进化 | `EvolutionSchedulerImpl` 支持定时自动调整、清理、重试 |
| 回滚方式 | 回滚到稳定技能/配置版本 | 回滚到最近一次 `source=manual` 的 brain-model 基线 |
| 候选选择 | 依赖技能与资源综合评估 | 由 `BrainModelSelector` / `BrainModelSelectorManager` 选择候选模型 |

---

## 三、旧架构中有、当前实现中没有完全覆盖的内容

- 自动生成技能代码
- 自动注册新技能到 `SkillRegistry`
- 对话 / 日志 / 指标 / 用户反馈的统一信号管道
- 进化结果自动写回知识库 / 绩效 / 运营评判的全链路联动
- 技能级人格演进与广义自我优化闭环

---

## 四、当前实现已经覆盖的能力

- 反馈落库与统计
- 按 brain 聚合统计
- 自动调整模型绑定
- 候选模型过滤与打分
- 自动 / 手工 / 回滚历史区分
- 最近 manual 基线回滚
- 调度执行与重试
- 管理端手工触发与历史查询

---

## 五、对外阅读建议

- 如果你想理解"为什么会有进化系统"，看"旧架构"那一列。
- 如果你想知道"现在系统到底做成了什么"，看"当前实现"那一列。
- 如果你准备继续开发，直接以当前实现为准，不要按旧架构补写不存在的能力。

---

## 六、结论

旧架构是一个更大的"企业生命体式进化"愿景；当前实现已经收敛成一个更可控、更可审计的 **brain-model 自动调整系统**。

因此这份文档的用途是：
- 快速看懂旧设计
- 快速识别当前差异
- 避免把历史构想误当成现状
