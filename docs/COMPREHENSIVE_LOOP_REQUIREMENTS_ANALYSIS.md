## 一、流程闭环定义

### 1.1 什么是闭环流程？

闭环流程是指具有完整处理链路的流程，必须包含：
```
输入 → 处理 → 输出 → 反馈 → 改进
```

**闭环流程特征**：
- 有明确的输入触发点
- 有完整的处理步骤
- 有输出结果或产物
- 有反馈机制（成功/失败、评分、审计日志等）
- 有改进机制（根据反馈优化下次处理）

**单向流程特征**：
- 只有输入→处理→输出
- 无反馈机制
- 无改进机制
- 一次性执行

**被动触发流程特征**：
- 由其他流程触发
- 不独立存在
- 通常作为其他闭环流程的子步骤

### 1.2 流程闭环必要性判断标准

| 判断维度 | 需要闭环 | 不需要闭环 |
|----------|---------|-----------|
| 业务重要性 | 核心业务流程 | 辅助支撑流程 |
| 状态管理 | 有状态流转（如审批状态） | 无状态变化（如一次性查询） |
| 结果验证 | 需要验证结果质量 | 结果无需验证 |
| 反馈机制 | 需要记录执行结果 | 不需要记录执行结果 |
| 持续优化 | 需要根据反馈改进 | 不需要改进 |
| 外部依赖 | 依赖外部系统（需同步状态） | 不依赖外部系统 |
| 数据一致性 | 涉及数据写入（需持久化） | 只读操作 |
| 错误恢复 | 失败需要自动恢复 | 失败无需处理 |

### 1.3 闭环验证表格格式（借鉴Claude Code）

> **借鉴来源**: Claude Code使用 `← 闭环：xxx` 注释标记流程闭环，并通过验证表格确保闭环完整性。Living Agent Service 借鉴此方法，为每个闭环需求添加验证表格。

**验证表格格式**：

| 阶段 | 入口条件 | 出口条件 | 闭环检查 |
|------|---------|---------|---------|
| 输入 | 触发条件 | 接收确认 | 输入已接收 |
| 处理 | 前置检查 | 处理完成 | 处理已执行 |
| 输出 | 处理成功 | 输出确认 | 输出已送达 |
| 反馈 | 输出完成 | 反馈记录 | 反馈已记录 |
| 改进 | 反馈分析 | 改进执行 | 改进已应用 |

**验证表格使用方法**：

1. **阶段**: 闭环流程的五个阶段（输入→处理→输出→反馈→改进）
2. **入口条件**: 进入该阶段的前置条件
3. **出口条件**: 离开该阶段的输出条件
4. **闭环检查**: 验证闭环完整性的检查点

**示例：闭环24 自愈闭环验证表格**：

| 阶段 | 入口条件 | 出口条件 | 闭环检查 |
|------|---------|---------|---------|
| 输入 | 异常事件触发 | 异常事件已记录 | 异常已检测 |
| 处理 | 异常类型识别 | 修复方案已生成 | 方案已决策 |
| 输出 | 修复方案确认 | 修复执行完成 | 修复已执行 |
| 反馈 | 修复执行完成 | 验证结果已记录 | 效果已验证 |
| 改进 | 验证结果分析 | 经验已沉淀 | 经验已应用 |

**子流程闭环拆分方法**：

> **借鉴来源**: Claude Code将主流程闭环拆分为子流程闭环（如Task工具拆分为6个子流程闭环）。Living Agent Service 为复杂闭环添加子流程闭环。

**子流程闭环格式**：

| 编号 | 子流程闭环名称 | 父闭环 | 核心价值 |
|------|--------------|--------|---------|
| X-A | 子流程1 | 闭环X | 子价值1 |
| X-B | 子流程2 | 闭环X | 子价值2 |

### 3.2 第25章遗漏的闭环需求（9个）

第25章只列出了14个闭环需求，遗漏了以下9个流程的闭环需求：

| 流程编号 | 流程名称 | 遗漏原因 | 闭环必要性 |
|----------|---------|---------|-----------|
| **17** | 前端与后端交互流程 | 被视为支撑流程，未单独列出 | WebSocket连接状态监控、API响应验证、前端状态同步需要闭环 |
| **18** | 数据库持久化流程 | 被PostgreSQL数据一致性闭环覆盖，但缺少表级闭环 | 每个表的写入验证、唯一约束检查、事务一致性需要单独闭环 |
| **19** | Native Rust与Java交互流程 | 被视为技术细节，未单独列出 | JNI调用结果验证、性能监控、异常处理需要闭环 |
| **20** | Python模型守护进程流程 | 被模型健康监控闭环覆盖，但缺少进程级闭环 | model_daemon.py进程存活监控、模型加载验证需要单独闭环 |
| **22** | Claude CLI代理流程 | 被视为辅助工具，未单独列出 | Claude CLI调用结果验证、可用性检查需要闭环 |
| **其他4个** | WebSocket连接管理闭环、消息Trace闭环、员工状态管理闭环、通道监控闭环 | 被其他闭环合并，但应该单独细化 | 每个子流程需要独立的闭环验证 |

## 四、补充闭环需求详细定义

## 八、自洽生命智能体闭环需求（新增7个）

> **设计目标**：让 living-agent-service 成为真正的自洽生命智能体——无需人工参与也能正常成长，同时兼容人工参与。
>
> **核心原则**：当前23个闭环覆盖了"流程正确性"，但缺少"生命体自洽性"闭环。一个真正的生命智能体需要：**自感知→自决策→自执行→自验证→自进化**。以下7个闭环正是补齐这一层。

### 8.1 闭环24：自愈闭环（Self-Healing）

```
┌──────────────────────────────────────────────────────────────────────────────────────────────┐
│            闭环24：自愈闭环（Self-Healing）                                                    │
├──────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                              │
│  闭环定义：                                                                                   │
│  异常检测 → 根因分析 → 补丁生成 → 应用/回滚 → 效果验证 → 经验沉淀                             │
│                                                                                              │
│  当前系统缺陷：                                                                               │
│  ├─ 异常能被捕获和记录，但无自动修复机制                                                        │
│  ├─ model_daemon.py 崩溃后无人自动重启                                                         │
│  ├─ Native JNI 调用失败后无重试策略                                                            │
│  ├─ 数据库连接断开后依赖 Spring 自动重连，但业务层无感知恢复                                    │
│  ├─ NamedPipe 断开后 NamedPipeModelClient 无自动重建                                           │
│                                                                                              │
│  闭环要素：                                                                                   │
│  ├─ 异常检测：HealthMonitorImpl 定时检查 + EvolutionCircuitBreaker 熔断信号                    │
│  ├─ 根因分析：ErrorCodeMapper（异常→代码→文档映射）自动定位                                    │
│  ├─ 补丁生成：PatchProposalService 创建补丁提案（含 confidence/rollbackAvailable）             │
│  ├─ 应用/回滚：PatchApplicationService 大脑自主决定应用或回滚                                  │
│  ├─ 效果验证：HealthMonitorImpl 重新检查 + EvolutionCircuitBreaker 确认恢复                    │
│  ├─ 经验沉淀：将修复过程写入 KnowledgeBase（L1→L2→L3 晋升）                                    │
│                                                                                              │
│  自洽关键点：                                                                                 │
```

### 8.9 闭环31：跨闭环协同编排闭环（Cross-Loop Orchestration）

> **设计背景**：闭环24-30各自由独立组件承担，但 L3 闭环之间存在强依赖（见 9.2 依赖关系图）。例如模型连续失败时，应同时触发闭环27（降级）→ 闭环24（自愈根因分析）→ 闭环26（修复经验沉淀），目前这些是孤立的。需要统一的协调入口避免"修复→引发新问题→再修复"震荡，并保证安全>自愈>降级>经济>知识>回执>个性的优先级。

```
┌──────────────────────────────────────────────────────────────────────────────────────────────┐
│            闭环31：跨闭环协同编排闭环（Cross-Loop Orchestration）                                │
├──────────────────────────────────────────────────────────────────────────────────────────────┤
│                                                                                              │
│  闭环定义：                                                                                   │
│  多闭环事件 → 优先级仲裁 → 协同编排 → 并行/串行执行 → 结果聚合 → 协同审计                        │
│                                                                                              │
│  当前系统缺陷：                                                                               │
│  ├─ 7个L3闭环各自独立运行，无统一协调入口                                                      │
│  ├─ EvolutionOrchestrator 只编排进化流程，不跨闭环                                              │
│  ├─ 并发触发时可能震荡：自愈修复→引发降级→触发个性变异→...                                       │
│  ├─ 闭环间无优先级仲裁，安全/经济/进化混在一起                                                  │
│                                                                                              │
│  闭环要素：                                                                                   │
│  ├─ 事件订阅：监听 HealthMonitor/ModelHealthRegistry/ComplianceManager/                       │
│  │            ExecutionReceiptReviewer/PersonalityMutation/BountyHunter 等关键事件             │
│  ├─ 优先级仲裁：安全(30) > 自愈(24) > 降级(27) > 回执(28) > 经济(25) > 知识(26) > 个性(29)      │
│  ├─ 协同编排：高优先级先执行，低优先级挂起；同类事件去重；冷却期内不重复触发                     │
│  ├─ 并行/串行：独立闭环可并行（如安全+知识），依赖闭环串行（自愈→经验沉淀）                     │
│  ├─ 结果聚合：一次协同周期内所有闭环执行结果汇总到 evolution_feedback 表                        │
│  ├─ 协同审计：StandardComplianceTraceService 记录完整协同决策链                                │
│                                                                                              │
│  自洽关键点：                                                                                 │
│  ├─ 无需人工：SelfGovernanceOrchestrator 按优先级自动调度                                       │
│  ├─ 兼容人工：协同冲突（同一资源被多闭环争抢）触发 InterventionNeuron 人工仲裁                  │
│  ├─ 闭环验证：每次协同周期都有 traceId，可追溯所有触发的子闭环                                  │
│  ├─ 防震荡：EvolutionCircuitBreaker 接入协同编排器，每个闭环设置冷却期                          │
│                                                                                              │
│  关键代码位置（新增）：                                                                       │
│  ├─ 协同编排器：core/evolution/orchestrator/SelfGovernanceOrchestrator.java（新增）           │
│  ├─ 事件总线：core/evolution/orchestrator/CrossLoopEventBus.java（新增）                       │
│  ├─ 优先级仲裁：core/evolution/orchestrator/LoopPriorityArbiter.java（新增）                  │
│  ├─ 协同结果聚合：core/evolution/orchestrator/CrossLoopAggregator.java（新增）                │
│  ├─ 复用：EvolutionOrchestrator / EvolutionCircuitBreaker / StandardComplianceTraceService   │
│                                                                                              │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```
